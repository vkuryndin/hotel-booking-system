# ADR-002. JWT и межсервисная авторизация

## 1. Контекст

Нужны роли USER/ADMIN, самостоятельная проверка JWT в микросервисах и защита операций Saga от пользовательского доступа. Проверки только на Gateway недостаточно: backend-сервисы должны контролировать права независимо от маршрутизации.

Кроме проверки подписи необходимо предусмотреть **досрочный отзыв пользовательских JWT**. Если изменился пароль или роль пользователя, ранее выданный токен не должен оставаться действительным до окончания своего срока жизни. При этом следует учитывать, что выпуск пользовательских токенов и сведения о пользователях находятся в Booking Service по архитектуре проекта.

**Основание:** ТЗ Skillfactory/МИФИ, требования к JWT, ролям, Resource Server и межсервисному взаимодействию.

## 2. Решение

Для системы выбирается **вариант №2 — самостоятельная проверка JWT каждым сервисом с централизованным контролем актуальности пользовательских токенов**.

Booking Service выпускает пользовательские JWT сроком действия один час и отдельные служебные JWT для операций Booking Service → Hotel Service. Gateway и бизнес-сервисы проверяют подпись и срок действия JWT через Spring Security Resource Server по публичным сертификатам. Права доступа разграничиваются ролями USER, ADMIN и SERVICE, включая ограничения `@PreAuthorize` и запрет вызова внутренних операций Saga через Gateway.

Для досрочного отзыва в пользовательский JWT включаются `tokenIdentity` и `tokenVersion`. При изменении роли или пароля версия токена пользователя увеличивается. Booking Service сравнивает значения из JWT с актуальным состоянием учётной записи; при несовпадении токен отклоняется. Gateway перед передачей защищённого пользовательского запроса проверяет статус токена через Booking Service. Служебные вызовы дополнительно защищены отдельным JWT и внутренним секретом Gateway.

## 3. Подверженные решению продукты

Hotel Booking System — Booking Service, Hotel Service и API Gateway.

## 4. Рассмотренные варианты

**Вариант 1. Только Gateway валидирует JWT.** Централизованная проверка на входе упрощает конфигурацию, но не защищает backend от прямого вызова. Локальная проверка JWT без обращения к состоянию учётной записи сама по себе не обеспечивает досрочный отзыв.

**Вариант 2. JWT на каждом сервисе, служебные токены и проверка актуальности через Booking Service.** Сохраняет независимую криптографическую проверку подписи и разграничение полномочий, позволяет досрочно отклонять ранее выданные пользовательские токены. Цена — зависимость Gateway от Booking Service при проверке актуальности.

**Вариант 3. Сессионная авторизация в общей БД.** Даёт централизованное управление сессиями, но вводит общую БД и не соответствует требованию использовать JWT.

**Вариант 4. Выделенный сервис аутентификации.** Отделяет выпуск токенов и контроль их актуальности от Booking Service, но требует дополнительного сервиса и изменения границ ответственности, не предусмотренных ТЗ.

## 5. Сравнение вариантов

| Критерий | Приоритет | Вариант 1 | **Вариант 2 (выбран)** | Вариант 3 | Вариант 4 |
|---|---|---|---|---|---|
| JWT и роли | MUST | Частично | **Да** | Нет | Да |
| Самостоятельная проверка JWT в backend-сервисах | MUST | Нет | **Да** | Нет | Да |
| Разделение пользовательских и служебных полномочий | MUST | Не предусмотрено | **Да** | Требует отдельного механизма | Да |
| Досрочный отзыв пользовательских JWT | SHOULD | Не предусмотрен | **Да** | Управление сессиями, не JWT | Да |
| Независимость проверки актуальности от Booking Service | SHOULD | Не проверяется | **Нет** | Нет | Да |
| Простота развёртывания | SHOULD | Выше | **Средняя** | Ниже | Ниже |

Приоритеты: **MUST** — обязательный; **SHOULD** — желательный; **COULD** — дополнительный.

**По результатам сравнения выбран вариант №2 — JWT на каждом сервисе, отдельные служебные токены и централизованная проверка актуальности через Booking Service.**

## 6. Последствия

**Положительные:** защита не ограничивается Gateway; пользовательские и межсервисные полномочия разделены; подпись JWT проверяется локально; смена роли или пароля позволяет досрочно сделать прежние токены недействительными без хранения каждого отозванного JWT в отдельном списке.

**Отрицательные:** необходимо управлять сертификатами и служебными секретами в нескольких сервисах. Контроль актуальности пользовательского JWT зависит от Booking Service: при его недоступности Gateway может отвечать `503 AUTH_SERVICE_UNAVAILABLE` на защищённые запросы, даже если Hotel Service доступен. Это сознательный компромисс в пользу контроля отзыва при сохранении предусмотренного ТЗ состава микросервисов.
