# ADR-001. Выбор микросервисной архитектуры

## 1. Контекст

ТЗ требует Gateway, Hotel Management Service, Booking Service и Eureka, независимые Spring Boot приложения и H2. Нужно разграничить источники истины, сохранив учебную сложность управляемой.

**Основание:** ТЗ Skillfactory/МИФИ, требования к микросервисам, безопасности, алгоритму занятости и распределённой согласованности.

## 2. Решение

**Принят вариант №2.** Четыре Spring Boot приложения: discovery-server, api-gateway, booking-service, hotel-service. Booking владеет пользователями и бронями; Hotel — отелями, номерами и слотами; Gateway обеспечивает вход и маршрутизацию, Eureka — discovery.

## 3. Подверженные решению продукты

Hotel Booking System — соответствующие компоненты: Booking Service, Hotel Service, API Gateway, Eureka Server.

## 4. Рассмотренные варианты

**Вариант 1. Монолитное приложение.** Проще локальные транзакции, но противоречит требованию отдельных сервисов и не демонстрирует discovery.

**Вариант 2. Четыре специализированных сервиса.** Соответствует ТЗ, сохраняет независимые области ответственности и раздельные H2.

**Вариант 3. Дополнительный User Service.** Усложняет межсервисные вызовы и администрирование, не требуется ТЗ.

## 5. Сравнение вариантов

| Критерий | Приоритет | Вариант 1 | **Вариант 2 (выбран)** | Вариант 3 |
|---|---|---|---|---|
| Соответствие ТЗ | MUST | Нет | **Да** | Частично |
| Разделение ответственности | MUST | Низкое | **Высокое** | Высокое |
| Простота сопровождения | SHOULD | Высокая | **Приемлемая** | Ниже |
| Издержки распределённости | COULD | Низкие | **Умеренные** | Выше |

Приоритеты: **MUST** — обязательный; **SHOULD** — желательный; **COULD** — дополнительный.

**По результатам сравнения выбран вариант №2 — Четыре специализированных сервиса.**

## 6. Последствия

Плюсы: локализованные границы ответственности, отдельные данные, динамическое обнаружение. Минусы: сетевые отказы, несколько процессов и необходимость корреляции/согласования. Связанные решения: ADR-002 и ADR-003.
