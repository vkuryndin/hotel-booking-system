# ADR-001. Выбор микросервисной архитектуры

## 1. Контекст

ТЗ требует Gateway, Hotel Management Service, Booking Service и Eureka, независимые Spring Boot приложения и H2. Нужно разграничить источники истины, сохранив учебную сложность управляемой.

**Основание:** ТЗ Skillfactory/МИФИ, требования к микросервисам, безопасности, алгоритму занятости и распределённой согласованности.

## 2. Решение

**Принят вариант №2.** Четыре независимых Spring Boot приложения: `discovery-server`, `api-gateway`, `booking-service`, `hotel-service`. Booking Service владеет пользователями, пользовательскими JWT и бронированиями; Hotel Service — отелями, номерами, их занятостью по датам и фотографиями. API Gateway является внешней точкой входа, выполняет маршрутизацию, проверки безопасности и передачу идентификатора трассировки. Eureka Server ведёт реестр экземпляров для обнаружения сервисов по логическому имени.

Граница владения данными закреплена на уровне хранения: у Booking Service и Hotel Service **разные H2 in-memory** и собственные JPA-сущности. Ни один бизнес-сервис не изменяет таблицы другого напрямую. Gateway и Eureka не ведут прикладную БД. Межсервисные операции выполняются HTTP-вызовами по обнаруженным адресам сервисов. Согласованность изменений в независимых базах обеспечивается механизмом Saga; для операций Booking → Hotel применяются служебные JWT ([ADR-002](002-security.md)).

Разделение данных означает, что сохранение бронирования и резервирование номера не могут быть одной локальной транзакцией. Booking Service координирует изменения в двух хранилищах с помощью Saga и компенсирующих действий (ADR-003). Доступность любого сервиса не предполагается постоянной: регистрация и обновление реестра Eureka происходят независимо от пользовательского запроса, а сетевые сбои учитываются на стороне вызывающего компонента (ADR-005).

## 3. Затронутые компоненты

Hotel Booking System — соответствующие компоненты: Booking Service, Hotel Service, API Gateway, Eureka Server.

## 4. Рассмотренные варианты

**Вариант 1. Монолитное приложение.** Проще локальные транзакции, но противоречит требованию отдельных сервисов и не демонстрирует discovery.

**Вариант 2. Четыре специализированных сервиса.** Соответствует ТЗ, сохраняет независимые области ответственности и две раздельные H2 бизнес-сервисов.

**Вариант 3. Дополнительный User Service.** Усложняет межсервисные вызовы и администрирование, не требуется ТЗ.

## 5. Сравнение вариантов

| Критерий | Приоритет | Вариант 1 | **Вариант 2 (выбран)** | Вариант 3 |
|---|---|---|---|---|
| Соответствие ТЗ | MUST | Нет | **Да** | Частично |
| Разделение ответственности | MUST | Низкое | **Высокое** | Высокое |
| Простота сопровождения | SHOULD | Высокая | **Приемлемая** | Ниже |
| Издержки распределённости | COULD | Низкие | **Умеренные** | Выше |

Приоритеты: **MUST** — обязательный; **SHOULD** — желательный; **COULD** — дополнительный.

**По результатам сравнения выбран вариант №2 — Четыре специализированных сервиса.**

## 6. Последствия

Плюсы: локализованные границы ответственности, отдельные данные, динамическое обнаружение. Минусы: сетевые отказы, несколько процессов и необходимость корреляции/согласования. Связанные решения: ADR-002 и ADR-003.
