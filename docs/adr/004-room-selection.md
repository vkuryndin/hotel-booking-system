# ADR-004. Алгоритмы выбора номера и защита занятости

## 1. Контекст

По ТЗ рекомендации должны быть на основе timesBooked по возрастанию с tie-break по ID. Нужно не путать операционный флаг available и занятость конкретного интервала.

**Основание:** ТЗ Skillfactory/МИФИ, требования к микросервисам, безопасности, алгоритму занятости и распределённой согласованности.

## 2. Решение

**Принят вариант №2 — выбор доступных номеров по датам с применением шаблона Strategy.** Сначала Hotel Service отбирает номера, у которых `available=true`, хватает вместимости и отсутствуют записи занятости в интервале **`[checkIn, checkOut)`**: дата выезда не считается занятой ночью. Операционный флаг `available` означает, что номер разрешён к продаже, но сам по себе не сообщает о его занятости на определённые даты.

Для отобранных номеров применяется `LeastBookedStrategy`: сортировка по `timesBooked` по возрастанию, при равенстве — по `id` по возрастанию. Дополнительная `MostExpensiveStrategy` сначала ранжирует категории **`SUITE → DELUXE → STANDARD`**, затем внутри каждой категории сортирует по цене за ночь по убыванию и при равной цене — по `id` по возрастанию. Стратегия сохраняется как настройка отеля (`LEAST_BOOKED` по умолчанию); параметр `strategy` в запросе рекомендации или автоматического бронирования переопределяет её только для текущего запроса.

Список рекомендаций не является блокировкой: за время между поиском и подтверждением другой запрос может занять номер. Поэтому **окончательная проверка выполняется при резервировании** в `RoomReservationService` внутри локальной транзакции Hotel Service: строка номера блокируется `PESSIMISTIC_WRITE`, а для каждой ночи создаётся запись в `room_reservation_nights` с уникальным ограничением `(room_id, night_date)`. Пересечение дат не допускается даже при конкурентных запросах. При конфликте ручной выбор завершается ошибкой, а автоматический подбор может перейти к следующему рекомендованному номеру.

`timesBooked` отражает число активных подтверждённых резервирований: увеличивается один раз при создании `RESERVED` и уменьшается один раз при переводе в `RELEASED`. Повторный запрос с тем же `reservationId` не изменяет счётчик повторно. Тем самым статистика применяется к подбору, но не заменяет контроль занятости по ночам.

## 3. Затронутые компоненты

Hotel Booking System — соответствующие компоненты: Booking Service и Hotel Service.

## 4. Рассмотренные варианты

**Вариант 1. Только флаг available.** Не учитывает даты и приводит к неверному запрету повторного использования номера.

**Вариант 2. LEAST_BOOKED + дата-слоты + Strategy.** Реализует обязательную сортировку `timesBooked/id` в режиме `LEAST_BOOKED` и позволяет использовать дополнительные стратегии.

**Вариант 3. Продвинутая ML/статистическая модель.** Сложнее, не требуется для учебной задачи.

## 5. Сравнение вариантов

| Критерий | Приоритет | Вариант 1 | **Вариант 2 (выбран)** | Вариант 3 |
|---|---|---|---|---|
| Верная занятость по датам | MUST | Нет | **Да** | Возможно |
| Сортировка timesBooked/id | MUST | Нет | **Да** | Не гарантирует |
| Расширяемость стратегий | SHOULD | Низкая | **Высокая** | Высокая |
| Трудоёмкость | COULD | Низкая | **Средняя** | Высокая |

Приоритеты: **MUST** — обязательный; **SHOULD** — желательный; **COULD** — дополнительный.

**По результатам сравнения выбран вариант №2 — LEAST_BOOKED, учёт занятости по датам и Strategy.**

## 6. Последствия

Плюсы: предсказуемый подбор `LEAST_BOOKED` с сортировкой по `timesBooked`, затем `id`; альтернативная стратегия с приоритетом категории, цены и `id`; возможность выбора альтернатив через дополнительный параметр API. Минусы: статистика `timesBooked` требует согласованности при отмене/компенсации, стратегии могут по-разному влиять на баланс нагрузки. Контроль параллельных слотов — часть доменной логики Hotel Service.
