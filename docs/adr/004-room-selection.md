# ADR-004. Алгоритмы выбора номера и защита занятости

**Статус:** Принято.

## 1. Контекст

По ТЗ рекомендации должны быть на основе timesBooked по возрастанию с tie-break по ID. Нужно не путать операционный флаг available и занятость конкретного интервала.

**Основание:** ТЗ Skillfactory/МИФИ, требования к микросервисам, безопасности, алгоритму занятости и распределённой согласованности.

## 2. Решение

**Принят вариант №2.** Выбран шаблон Strategy: `LeastBookedStrategy` сортирует по `timesBooked`, затем `id`; дополнительная `MostExpensiveStrategy` сначала ранжирует номера по категории (`SUITE`, `DELUXE`, `STANDARD`), затем внутри категории по убыванию стоимости за ночь, а при равенстве стоимости — по возрастанию `id`. В Hotel Service доступность по датам вычисляется по резервированиям/ночам, а не по `available`. Стратегия настраивается на уровне отеля; параметр `strategy` в запросе рекомендации или автоматического бронирования может временно переопределить её для одной операции. При отсутствии параметра действует настройка отеля (`LEAST_BOOKED` по умолчанию).

## 3. Затронутые компоненты

Hotel Booking System — соответствующие компоненты: Booking Service и Hotel Service.

## 4. Рассмотренные варианты

**Вариант 1. Только флаг available.** Не учитывает даты и приводит к неверному запрету повторного использования номера.

**Вариант 2. LEAST_BOOKED + дата-слоты + Strategy.** Реализует обязательную сортировку `timesBooked/id` в режиме `LEAST_BOOKED` и позволяет использовать дополнительные стратегии.

**Вариант 3. Продвинутая ML/статистическая модель.** Сложнее, не требуется для учебной задачи.

## 5. Сравнение вариантов

| Критерий | Приоритет | Вариант 1 | **Вариант 2 (выбран)** | Вариант 3 |
|---|---|---|---|---|
| Верная занятость по датам | MUST | Нет | **Да** | Возможно |
| Сортировка timesBooked/id | MUST | Нет | **Да** | Не гарантирует |
| Расширяемость стратегий | SHOULD | Низкая | **Высокая** | Высокая |
| Трудоёмкость | COULD | Низкая | **Средняя** | Высокая |

Приоритеты: **MUST** — обязательный; **SHOULD** — желательный; **COULD** — дополнительный.

**По результатам сравнения выбран вариант №2 — LEAST_BOOKED, учёт занятости по датам и Strategy.**

## 6. Последствия

Плюсы: предсказуемый подбор `LEAST_BOOKED` с сортировкой по `timesBooked`, затем `id`; альтернативная стратегия с приоритетом категории, цены и `id`; возможность выбора альтернатив через дополнительный параметр API. Минусы: статистика `timesBooked` требует согласованности при отмене/компенсации, стратегии могут по-разному влиять на баланс нагрузки. Контроль параллельных слотов — часть доменной логики Hotel Service.
